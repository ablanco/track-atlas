# User Model Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the first user table and establish automatic audit timestamps for all application models, without implementing authentication flows.

**Architecture:** Drizzle defines the PostgreSQL users table and exports inferred select/insert types. Database defaults supply identifiers and creation timestamps; a PostgreSQL trigger maintains modification timestamps for both Drizzle and direct SQL updates. A shared timestamp-column factory and documented trigger convention support future models.

**Tech Stack:** Existing Drizzle ORM 0.45.x, Drizzle Kit 0.31.x, PostgreSQL 18/PostGIS, TypeScript, node:test/tsx.

**Spec:** Approved in this conversation: required first name, last name, email, password, and date of birth; optional display name and avatar; email/password local login initially; future social login deferred; password storage must be a securely salted hash, never plaintext; all models need automatic creation/modification timestamps; users need an active flag for disabling accounts. Case-insensitive unique emails and active=true were proposed and accepted. This step is database model, migration, tests, and documentation only; registration, hashing, and login flows are explicitly deferred.

## Model Decisions

These implementation details are proposed by the implementer, not additional user requirements:

| TypeScript field | SQL column      | Definition                                                                                             |
| ---------------- | --------------- | ------------------------------------------------------------------------------------------------------ |
| `id`             | `id`            | UUID primary key, generated by PostgreSQL with `gen_random_uuid()`                                     |
| `firstName`      | `first_name`    | Required nonblank text                                                                                 |
| `lastName`       | `last_name`     | Required nonblank text                                                                                 |
| `displayName`    | `display_name`  | Nullable text; not a unique login identifier                                                           |
| `email`          | `email`         | Required nonblank text; no surrounding spaces; unique index on `lower(email)`                          |
| `passwordHash`   | `password_hash` | Required nonblank text; encoded hash including algorithm parameters and salt                           |
| `dateOfBirth`    | `date_of_birth` | Required PostgreSQL `date`, represented as `YYYY-MM-DD` string in TypeScript, not a JavaScript instant |
| `avatarUrl`      | `avatar_url`    | Nullable text URL/reference; no upload/storage functionality                                           |
| `active`         | `active`        | Required boolean, defaults to `true`                                                                   |
| `createdAt`      | `created_at`    | Required `timestamptz`, defaults to database `now()`                                                   |
| `updatedAt`      | `updated_at`    | Required `timestamptz`, defaults to database `now()`, set to `statement_timestamp()` on every update   |

Email casing may be preserved for display; the functional unique index defines identity. Full email syntax validation belongs in the future input layer. Nonblank checks use PostgreSQL `btrim`; do not assume the database verifies that arbitrary text is a cryptographic hash. A future social-only account design can revisit the required local credential; no nullable password is introduced prematurely.

## Review Focus

- Differently cased copies of an email must not create separate accounts, even if one is inactive.
- Direct SQL updates must maintain `updatedAt`, not just queries passing through Drizzle.
- Birthday values must remain calendar dates across connection time zones.
- Missing required fields must be rejected while omitted optional fields remain null and active defaults true.
- Migration replay and test cleanup must preserve existing PostGIS and unrelated records.
