# Signup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (native execution) or superpowers:subagent-driven-development if explicitly selected by the user. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let signed-out visitors create an account, automatically sign in, and return to the localized homepage.

**Architecture:** A localized Server Action form calls a server-only signup service. Asynchronous salted scrypt hashing precedes a transaction that inserts the user and a digest-only opaque session; request-time session lookup gates both the form and submission. Preserve the existing static homepage shell with Suspense around auth-dependent UI.

**Tech Stack:** Next.js 16.4 Cache Components, React 19, next-intl 4, Drizzle 0.45, PostgreSQL 18/PostGIS, Node.js crypto, node:test/tsx, Playwright. No new runtime dependency is required.

**Spec:** `docs/superpowers/specs/2026-10-15-signup-design.md` (approved).

## Global Constraints

- Work directly on `master`; do not create branches/worktrees. Leave implementation uncommitted until requested; the earlier commit/push request was already fulfilled.
- Required: first name, last name, email, date of birth, password. Display name optional; avatar excluded. No confirmation password, strength requirements, CAPTCHA, login/sign-out UI, email verification, OAuth, or age eligibility policy.
- Routes `/en/signup`, `/es/signup`; `/signup` uses existing locale negotiation. Successful signup and signed-in signup access return to the localized homepage.
- Layout A: open form with names sharing a desktop row and stacking on mobile; preserve English/Spanish, light/dark themes, accessibility, and homepage honesty about unimplemented tracks/uploads.
- Trim names/display name/email; do not trim/normalize passwords. Names/display name at most 200 characters, email at most 254 characters, password at most 1,024 UTF-8 bytes and nonempty. Whitespace-only passwords remain valid in this policy-free slice.
- Birthdays are real calendar dates from year 0001 through today (UTC), represented as `YYYY-MM-DD` strings, without timezone conversion or age threshold.
- scrypt: `N=32768`, `r=8`, `p=3`, fresh salt at least 16 bytes, 64-byte key, explicit maxmem at least 64 MiB, asynchronous, versioned encoding. Bound concurrent hashing and never queue it without limit.
- Sessions: random 32-byte token; SHA-256 digest only in database; fixed 30-day lifetime calculated by database; cookie `track_atlas_session`, HttpOnly, SameSite=Lax, Path=/, no Domain, Secure in production.
- New models spread fresh `auditColumns()` and attach `public.set_updated_at()` in a new migration. Never modify applied migrations.
- No publicly cached auth state. Never expose passwords/hashes/tokens in action state, markup, logs, or URLs. Only the cookie receives the raw session token.
- Follow installed Next.js guides before implementation, including authentication-with-cache-components, forms, cookies, and Server Actions. Use Phosphor individual imports for any icons added.

## Review Focus

- Submitting a captured signup action while already signed in must not create another user (Task 4 browser test).
- A database outage during session lookup must not silently authorize signup as a guest (Tasks 2/4 failure tests).
- Two concurrent submissions for differently cased versions of the same email create one account/session, never overwrite or authenticate the existing account (Task 3 live test).
- Unicode password byte limits and leap-day/year-0001 birthdays must not be corrupted by string trimming or JavaScript date rollover (Task 1 unit tests).
- Authenticated navigation must never leak a viewer's state to another browser or serve a cached guest signup form after success (Task 4 isolated-context and back-navigation tests).

### Task 1: Input validation and secure password hashing

**Files:** Create `auth/validation.ts`, `auth/password.ts`, `tests/auth/validation.test.ts`, `tests/auth/password.test.ts`; modify `package.json`.

**Interfaces:**

- `SignupValues = { firstName: string; lastName: string; displayName: string; email: string; dateOfBirth: string }` (never contains password).
- `SignupInput = Omit<SignupValues, 'displayName'> & { displayName: string | null; password: string }`.
- `SignupField = keyof SignupValues | 'password'`; `ValidationCode = 'required' | 'tooLong' | 'invalid' | 'future'`.
- `validateSignup(form: FormData, today: string): { ok: true; input: SignupInput; values: SignupValues } | { ok: false; errors: Partial<Record<SignupField, ValidationCode>>; values: SignupValues }`.
- `hashPassword(password: string): Promise<string>`; exported `HashBusyError` for capacity rejection; maximum two active hashes per process, no waiting queue.
- Encoding: `$scrypt$v=1$N=32768,r=8,p=3$<base64url salt>$<base64url 64-byte key>`; random 16-byte salt; maxmem 64 MiB.

- [ ] Write table-driven validation tests with a fixed `today='2026-10-15'`: missing/repeated/File-valued required fields fail; optional display name omitted/blank becomes null; whitespace-only names fail; trims names/email but preserves email case and password spaces. Assert forbidden fields never reach input, and password never appears in `values` or failure results.
- [ ] Pin valid dates `0001-01-01`, `2000-02-29`, `2026-10-15`; reject `1900-02-29`, `2026-02-30`, `0000-01-01`, malformed dates, and `2026-10-16`. Compare calendar components, not UTC instants (JavaScript years 0–99 require care).
- [ ] Pin name/display bounds 200/201, email 254/255, password `'x'` accepted, 1,024 ASCII bytes accepted/1,025 rejected, `'é'.repeat(512)` accepted/513 rejected. Repeated optional display names also fail; missing optional value succeeds. Validate common email structure and reject control/embedded-whitespace characters without inventing a full RFC mailbox parser.
- [ ] Write hashing tests: same password hashes differ; parse each encoding and independently derive with Node scrypt to match stored key; leading/trailing spaces change the derived result. Start three calls synchronously, assert exactly two complete and one rejects `HashBusyError`; after settling, another succeeds. A rejected hash operation must release capacity.
- [ ] Run `pnpm exec tsx --conditions=react-server --test tests/auth/*.test.ts`; observe missing exports/modules fail before implementation.
- [ ] Implement interfaces, allowlist validation, code-point-aware character counts (`Array.from(value).length`), UTF-8 password bounds, versioned salted async hashing and try/finally capacity release. Limit safe echoed values to bounded expected strings; reject invalid types/multiplicity instead of echoing them. `auth/password.ts` imports `server-only`; validation remains framework-independent. Use real crypto, not a hash mock.
- [ ] Add `test:auth`: `tsx --conditions=react-server --test tests/auth/*.test.ts`; run `pnpm test:auth` and `pnpm exec tsc --noEmit`, expect exit 0.

### Task 2: Database sessions and request-time authentication

**Files:** Create `auth/database.ts`, `auth/session-store.ts`, `auth/session.ts`, `tests/db/sessions.test.ts`, `tests/auth/session.test.ts`; modify `db/schema.ts`, migration SQL/metadata, `package.json`.

**Interfaces:**

- `Database = ReturnType<typeof createDatabase>['db']`; `AuthDatabase = Pick<Database, 'select' | 'insert' | 'transaction'>`; `AuthExecutor = Pick<Database, 'select' | 'insert'>`. Transaction handles must structurally satisfy these types; prove that in tests/tsc.
- Export `sessions`, inferred `Session`/`NewSession` types from schema; columns `id`, `userId`, `tokenHash`, `expiresAt`, `createdAt`, `updatedAt`.
- `SessionIdentity = { userId: string }`; `IssuedSession = { token: string; expiresAt: Date }`.
- `createSession(executor: AuthExecutor, userId: string): Promise<IssuedSession>`; `findSessionUser(executor: AuthExecutor, token: string | undefined): Promise<SessionIdentity | null>`.
- `getCurrentUser(): Promise<SessionIdentity | null>` reads cookie and calls lookup using lazy `getDb()`; short-circuits absent/malformed cookies before opening DB. Infrastructure failures propagate.
- `sessionCookieOptions(expiresAt: Date, production: boolean)` returns typed cookie options; `SESSION_COOKIE_NAME='track_atlas_session'`.

- [ ] Write live SQL-first tests that fail against missing `sessions`: UUID/audit defaults; non-null columns; unique digest; FK enforcement; user deletion cascade; timestamp trigger on direct SQL update. Use own clients/transactions with rollback and release.

- [ ] Write unit tests for exact development/production cookie attributes and malformed-token short circuit. Add a targeted executor failure test proving a real thrown database lookup error is propagated, not converted to null. Mock only this failure boundary, not normal persistence behavior.
- [ ] Run targeted live tests; observe missing table/exports fail. ### Task 3: Transactional signup service

**Files:** Create `auth/signup.ts`, `tests/db/signup.test.ts`; extend `test:db` in `package.json`.

**Interfaces:**

- Consumes `SignupInput`, `AuthDatabase`, `hashPassword`, `createSession` from Tasks 1/2.
- `SignupResult = { ok: true; session: IssuedSession } | { ok: false; reason: 'emailTaken' | 'unavailable' }`.
- `registerUser(db: AuthDatabase, input: SignupInput): Promise<SignupResult>` hashes before transaction, inserts allowlisted user fields and session in transaction, then returns only session info. It never sets a cookie or redirects; callers must validate and enforce guest status first.

- [ ] Write live tests for minimal/full signup: one active user and one session, null avatar, null/retained display name, correct birthday, independently verified hash. The session authenticates only the inserted user. No plaintext or hash in service result.
- [ ] Test duplicate/different-case email including disabled original: returns `emailTaken`, does not modify original user or add a session. Test two truly concurrent connections registering same address with different casing: exactly one success, one `emailTaken`, one user and one session; use unique fixture email and explicit cleanup.
- [ ] Test session-insert failure rolls back newly inserted user. Use a narrowly scoped executor/transaction failure seam or fixture-specific database rejection; do not install broad production triggers or monkeypatch shared global database state. Cover actual transaction rollback through the real database.
- [ ] Test database and hash-capacity failures return `unavailable` with no secrets and no partial account. Only SQLSTATE 23505 for the named user email index is `emailTaken`; handle Drizzle's wrapped cause rather than misclassifying every uniqueness error.
- [ ] Run `pnpm exec tsx --conditions=react-server --test tests/db/signup.test.ts`, observe RED, then implement the service. Return known safe classifications without logging raw exceptions/input. Do not catch the later Next.js redirect here.
- [ ] Use rollback-isolated transaction handles wherever feasible. Tests requiring real commits/concurrency track only their unique IDs/addresses and delete those in finally; use existing cascade for sessions. Add test path and `--conditions=react-server` to `test:db` so server-only service imports are testable; run auth/live suites and tsc, expect exit 0.
